How it all fits together

You edit the site on your computer. Git records each change. GitHub stores the code and, through GitHub Actions, copies it to your Hostinger server automatically. Two branches decide where the code goes:

Key idea: you never upload files by hand. Push to dev to update staging. Merge into main to update live. The server's own .env file (passwords, keys) is never in git and is never overwritten.

1. One-time setup

These steps were used to set up staging. Repeat them for the live site, or use them to fix or rebuild the pipeline. Not needed for everyday work: pushing to GitHub is enough, because the deploy runs from GitHub Actions. Only whoever manages the server needs the SSH key and secrets.

Create a deploy key on your computer

A key pair is a lock and a key. The private key stays on your computer and in a GitHub secret. The public key goes to Hostinger. Keep both outside the project folder (in .ssh).

PowerShell on your computer
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\gonetherlandtours_deploy" -C "github-deploy-gonetherlandtours" -N '""'
Add the public key to Hostinger

Show it, copy the single ssh-ed25519 ... line, then in hPanel go to Advanced > SSH Access > Add SSH key.

PowerShell on your computer
Get-Content "[KEY].pub"
Test the login from your computer

It should print connected. The first time, answer yes to the fingerprint question.

PowerShell on your computer
ssh -i "[KEY]" -p [PORT] [USER]@[HOST] "echo connected"
Add the GitHub secrets

On GitHub open your repository > Settings > Secrets and variables > Actions > New repository secret (the repository's Settings, not your personal ones). Names must match exactly:

Secret nameValue
STAGING_SSH_KEYThe whole private key file, including the BEGIN and END lines
STAGING_HOST[HOST]
STAGING_PORT[PORT]
STAGING_USER[USER]
STAGING_PATH/home/[USER]/domains/[STG]/app

Show the private key to copy it (never paste it in chat, email or the project folder):

PowerShell on your computer
Get-Content "[KEY]" -Raw
Server folder layout (already done on staging)

The project lives in an app folder and public_html is a link to app/public. That keeps your code and .env out of the public web folder. The folder is a git clone, so the server can run git pull.

Prove the pipeline works

Push any commit to dev, open the repo's Actions tab, and look for a green tick on "Deploy staging". Then open the staging site.

"Run workflow" button missing? GitHub only shows it for workflows that exist on the default branch (main). Pushing to dev still triggers the deploy normally.

2. Daily workflow

Use this every time you change the site.

Make sure you are on the dev branch
PowerShell, in the project folder
cd "PATH\TO\gonetherlandtours"   # the folder where you cloned the repo
git checkout dev
git pull
Make your changes and run the tests
Project folder
php artisan test

If you changed CSS, JavaScript or Tailwind classes, rebuild the assets. The server has no Node, so the built files are committed:

Project folder
npm run build
Check what changed
Project folder
git status

Look for anything that should not be there: .env, keys, passwords. Those must never be committed.

Commit with a clear message
Project folder
git add -A
git commit -m "Describe what you changed in one line"
Push to dev: this updates staging
Project folder (or use Sync Changes in VS Code)
git push origin dev

Then watch GitHub > Actions > Deploy staging. Green tick = deployed (takes about 15 to 60 seconds). Red cross = open the run and read the log (see Troubleshooting).

Test on staging

Open the staging address, check the pages you changed on phone and desktop, and send a test enquiry. Do not go live until this passes.

Good habits: small commits with clear messages; pull before you start; never edit files directly on the server (the next deploy could clash with them); one change at a time so a problem is easy to undo.

3. Go live to do

A. Before you touch the server

Replace placeholders and sample content

Everything marked [CONFIRM: ...] or "Sample": team members, tour type page copy, prices, testimonials, FAQ answers, legal pages, real photos. The full list is in docs/reference/CONTENT_TO_CONFIRM.md. Do it on staging first.

Real packages are indexable

In Admin > Packages, untick Hide from search engines on real packages and delete the "Sample:" packages. Sample packages are hidden from Google on purpose.

Register the live domain for reCAPTCHA

At google.com/recaptcha/admin create a v2 checkbox key for the live domain. The test keys must not be used live (the form would be open to spam).

Point the domain at Hostinger and add the website in hPanel

Add the live domain as a website in hPanel, set the nameservers or DNS as Hostinger instructs, and turn on the free SSL certificate. DNS can take from minutes to a day.

B. Create the live site on the server

Same layout as staging: the project in app, with public_html linking to app/public. Connect first:

PowerShell on your computer
ssh -i "[KEY]" -p [PORT] [USER]@[HOST]

Then, on the server:

Clone the main branch into an app folder
On the server
cd ~/domains/[DOM]
mv public_html public_html_old     # only if it is the empty default folder
git clone -b main git@github.com:Profitable-Tradesmen/gonetherlandtours.git app
ln -s app/public public_html

The server already has GitHub access (the same one staging uses). If the clone says "permission denied", ask the project lead.

Create the database

In hPanel > Databases create a MySQL database, user and password. Note the three values for the next step.

Create the live .env
On the server
cd ~/domains/[DOM]/app
cp .env.example .env
nano .env

Set at least these (save in nano with Ctrl+O, Enter, Ctrl+X):

APP_NAME=GoNetherlandTours
APP_ENV=production
APP_DEBUG=false
APP_URL=https://[DOM]
SITE_NOINDEX=false
DB_HOST=localhost
DB_DATABASE=...        # from hPanel
DB_USERNAME=...
DB_PASSWORD=...
SESSION_DRIVER=database
CACHE_STORE=database
QUEUE_CONNECTION=database
MAIL_MAILER=smtp
MAIL_HOST=smtp.hostinger.com
MAIL_PORT=465
MAIL_USERNAME=...      # your hPanel mailbox
MAIL_PASSWORD=...
MAIL_FROM_ADDRESS="enquiries@[DOM]"
RECAPTCHA_SITE_KEY=... # real keys
RECAPTCHA_SECRET_KEY=...
ADMIN_SEED_EMAIL=you@[DOM]
ADMIN_SEED_PASSWORD=a-long-unique-password   # delete this line after the first seed
SITE_NOINDEX must be false on live. If it is true, the whole site tells Google not to list it. Keep it true on staging.
First install (one time only)
On the server, in the app folder
/opt/alt/php84/usr/bin/php $(command -v composer) install --no-dev --optimize-autoloader --no-interaction
/opt/alt/php84/usr/bin/php artisan key:generate --force
/opt/alt/php84/usr/bin/php artisan migrate --force --seed
/opt/alt/php84/usr/bin/php artisan storage:link
/opt/alt/php84/usr/bin/php artisan config:cache
/opt/alt/php84/usr/bin/php artisan view:cache
Never run migrate:fresh on a live site (it erases the database). --seed is for the very first install only: later deploys use plain migrate --force, which deploy.sh already does.
Add the cron job (emails and GoHighLevel sync)

hPanel > Advanced > Cron Jobs, every minute:

* * * * * cd /home/[USER]/domains/[DOM]/app && /opt/alt/php84/usr/bin/php artisan schedule:run >> /dev/null 2>&1
Visit the site and log in

Open https://[DOM], then /admin/login. Change the admin password, then remove ADMIN_SEED_PASSWORD from the live .env.

Optional but wise: create a GitHub Environment named production with "Required reviewers", so every live deploy needs your approval click.

Final staging check

Everything you want live must already work on staging, including a test enquiry reaching GoHighLevel.

Merge dev into main: this deploys live

Easiest and safest: on GitHub open Pull requests > New pull request, base main, compare dev, review the changes, then Merge. Watch Actions > Deploy live for a green tick.

Command-line alternative:

Project folder
git checkout main
git pull
git merge dev
git push origin main
git checkout dev

D. Live checks

Check the live site

Home, a package, /tours/self-drive, /faq, /testimonials, /about, /contact; the padlock (HTTPS) shows; /robots.txt says Allow: / (not Disallow: /); /sitemap.xml lists your pages.

Connect GoHighLevel on live

Admin > GoHighLevel: enter the Location ID and token, tick "Send enquiries", Save, then Test connection and Create missing custom fields. Required scopes: contacts.readonly, contacts.write, locations/customFields.readonly, locations/customFields.write.

Send a test enquiry on every form

Quiz, pop-up, package quote, contact. Use a new email and a new phone number each time (GoHighLevel merges contacts that share an email or phone). Confirm the staff email, the admin inbox and the GoHighLevel contact.

Fill Admin > Settings

Company name, phone, email, address, social links, notification emails, Google Tag Manager ID, logo.

4. After launch

Google Search Console

Verify the domain and submit https://[DOM]/sitemap.xml.

Google Tag Manager and Ads conversion

Attach the conversion to the enquiry_thank_you event and test in Tag Assistant (see FORMS_AND_TRACKING.md).

Troubleshooting

What you seeLikely cause and fix
Deploy run fails in a few secondsA GitHub secret is missing or misspelled. Check all five names and values. Names are case-sensitive and secrets cannot be viewed after saving, only replaced.
Log says Permission denied (publickey)The public key is not in Hostinger SSH Keys, or the secret holds the wrong file. The secret must be the private key (starts with -----BEGIN OPENSSH PRIVATE KEY-----).
Log says git pull failed or "not possible to fast-forward"Someone changed files directly on the server. SSH in, run git status, and ask the project lead before discarding anything.
Deploy is green but the page looks oldHard refresh (Ctrl+F5). If still old, the server cache may need clearing: php artisan optimize:clear then config:cache and view:cache.
Page shows "500 | Server Error"Set APP_DEBUG=true briefly on staging only, reload, read the message, then set it back. The log is storage/logs/laravel.log.
Styles or images missingYou changed CSS/JS but did not run npm run build and commit public/build before pushing.
GoHighLevel test says "token is not authorized for this scope"Edit the integration in GoHighLevel (Settings > Private Integrations), tick the missing scope, save, test again.
GoHighLevel keeps updating the same contactIt matches on email or phone. Use a different phone number for each test.
Google does not list the siteCheck SITE_NOINDEX=false on live, packages are not set to hide from search engines, and the sitemap is submitted.

Undo a bad deploy

Do not edit the server. Revert the bad commit on your computer and push; the deploy puts the old behaviour back. Find the commit with git log --oneline.

Project folder
git checkout dev
git revert COMMIT_ID
git push origin dev

For live, merge the fixed dev into main the same way as a normal release. A reverted commit that contained a database migration does not undo the database change: ask the project lead first.

Safety rules

  • Never commit .env, private keys, passwords or API tokens. If one is committed by mistake, treat it as exposed: revoke it and make a new one. Deleting it from git is not enough because history keeps it.
  • Keep SSH keys in C:\Users\Tonix\.ssh, never in the project folder.
  • Never paste a private key or token into chat, email or a document.
  • Never run migrate:fresh or delete the database on live.
  • Never edit code directly on the server. Change it locally, push, let the deploy copy it.
  • Staging keeps SITE_NOINDEX=true. Live uses false.
